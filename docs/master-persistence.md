# Master Persistence Design

This document defines the first Master persistence slice for Worker Nodes,
service placement, desired state and observed actual state. It is an
implementation boundary, not a change to the domain or C4 models.

## Ownership

The Master owns these records and is the only component that writes them.
Master application components use repositories; API handlers, schedulers and
reconciliation code do not issue SQL directly. Worker Agents communicate with
Master over HTTP and never access PostgreSQL.

The schema references the existing `service` domain entity. Service-specific
configuration remains outside this slice.

## Relational schema

PostgreSQL types below are logical types for the first implementation. UUIDs
are generated by the application or database consistently across all Master
entities.

### `worker_nodes`

| Column | Type | Required | Constraints / meaning |
| --- | --- | --- | --- |
| `id` | UUID | yes | Primary key |
| `hostname` | text | yes | Node identity; not necessarily a resolvable DNS name |
| `lifecycle` | text | yes | `ACTIVE`, `SUSPENDED`, `STOPPED`, or `DELETED` |
| `reconciliation_condition` | text | yes | `PENDING`, `RECONCILING`, `READY`, `DEGRADED`, `ERROR`, or `UNKNOWN` |
| `capabilities` | JSONB | yes | Supported service families and provider capabilities; default `{}` |
| `cpu_capacity` | numeric | yes | Schedulable capacity; non-negative |
| `memory_capacity` | bigint | yes | Schedulable bytes; non-negative |
| `disk_capacity` | bigint | yes | Schedulable bytes; non-negative |
| `cpu_usage` | numeric | yes | Latest reported usage; non-negative |
| `memory_usage` | bigint | yes | Latest reported bytes; non-negative |
| `disk_usage` | bigint | yes | Latest reported bytes; non-negative |
| `last_heartbeat_at` | timestamptz | no | Latest accepted heartbeat |
| `created_at` | timestamptz | yes | Creation time |
| `updated_at` | timestamptz | yes | Last Master-side update |

Constraints and indexes:

- `hostname` is unique for nodes that are not decommissioned; a node identity
  cannot be registered twice while active.
- Usage must not be negative. Capacity validation belongs to the Master domain
  layer and must also prevent allocation beyond capacity.
- Index `status` and `last_heartbeat_at` for node monitoring and scheduling.
- `capabilities` is queried by supported service family; provider-specific
  capability validation remains outside the database constraint layer.

### `service_assignments`

| Column | Type | Required | Constraints / meaning |
| --- | --- | --- | --- |
| `id` | UUID | yes | Primary key |
| `service_id` | UUID | yes | Foreign key to `services.id` |
| `worker_node_id` | UUID | yes | Foreign key to `worker_nodes.id` |
| `status` | text | yes | `ASSIGNED`, `DRAINING`, or `RELEASED` |
| `assigned_at` | timestamptz | yes | Time this assignment became effective |
| `released_at` | timestamptz | no | Set when the assignment is released |
| `created_at` | timestamptz | yes | Creation time |
| `updated_at` | timestamptz | yes | Last Master-side update |

Constraints and indexes:

- Foreign keys use restrictive deletion behavior. A node or service cannot be
  deleted while an assignment still refers to it.
- At most one assignment for a service may be active (`ASSIGNED` or
  `DRAINING`). This is a partial unique index on `service_id`.
- Index `(worker_node_id, status)` for capacity and node inspection.
- Assignment history is retained as released rows; replacement is an explicit
  state transition, not an overwrite that loses placement history.

### `desired_states`

| Column | Type | Required | Constraints / meaning |
| --- | --- | --- | --- |
| `service_id` | UUID | yes | Primary key and foreign key to `services.id` |
| `version` | bigint | yes | Monotonically increasing per service; starts at `1` |
| `lifecycle_state` | text | yes | Desired service lifecycle state |
| `configuration` | JSONB | yes | Provider-neutral desired configuration; default `{}` |
| `updated_at` | timestamptz | yes | Time the desired version was committed |

A desired-state update replaces the current row and increments `version` in
the same transaction as its assignment change. The version is scoped to one
service, not globally to the database.

### `actual_states`

| Column | Type | Required | Constraints / meaning |
| --- | --- | --- | --- |
| `service_id` | UUID | yes | Primary key and foreign key to `services.id` |
| `version` | bigint | yes | Desired-state version represented by this observation |
| `lifecycle_state` | text | yes | Agent-reported actual lifecycle state |
| `reconciliation_condition` | text | yes | Agent-reported actual reconciliation status |
| `configuration` | JSONB | yes | Latest observed provider configuration; default `{}` |
| `health` | JSONB | yes | Latest observed health and diagnostics; default `{}` |
| `observed_at` | timestamptz | yes | Observation time supplied by the Agent |
| `updated_at` | timestamptz | yes | Time the observation was accepted by Master |

An actual-state report is accepted only when it belongs to the current
assignment and is not older than the stored observation for that service.
Reports for an older desired version cannot overwrite a newer version. The
repository must perform this check atomically with the upsert.

### `reconciliation_attempts`

| Column | Type | Required | Constraints / meaning |
| --- | --- | --- | --- |
| `service_id` | UUID | yes | Primary key and foreign key to `services.id` |
| `assignment_id` | UUID | yes | Unique ID for to use for identify the attempt |
| `desired_version` | bigint | yes | Desired-state version represented by this observation |
| `status` | text | yes | Agent-reported reconciliation attempt status |
| `error_code` | bigint | yes | Agent-reported error code; default 0 |
| `error_message` | text | yes | Agent-reported error message; default `` |
| `started_at` | timestamptz | yes | Reconciliation attempt start time |
| `finished_at` | timestamptz | yes | Reconciliation attempt finish time |

An actual-state report is accepted only when it belongs to the current
assignment and is not older than the stored observation for that service.
Reports for an older desired version cannot overwrite a newer version. The
repository must perform this check atomically with the upsert.

## Repository boundaries

Repositories expose domain-oriented operations and return domain objects or
explicit not-found/conflict results. They do not expose SQLAlchemy sessions
to callers.

### `WorkerNodeRepository`

- `get(node_id)` and `list(status=None, capability=None)`
- `create(node)`
- `update_health(node_id, status, usage, last_heartbeat_at)`
- `reserve_capacity(node_id, allocation)` with an atomic capacity check
- `decommission(node_id)` only when no active assignments remain

### `ServiceAssignmentRepository`

- `get_active_for_service(service_id)`
- `list_for_node(node_id, active_only=True)`
- `create_or_replace(service_id, worker_node_id, status)`
- `release(assignment_id)`
- `validate_current(service_id, assignment_id)` for reconciliation reports

Assignment replacement is called only inside the placement transaction. The
repository does not select nodes and does not implement failover policy.

### `DesiredStateRepository`

- `get(service_id)`
- `put_next(service_id, lifecycle_state, configuration)` which increments the
  per-service version under row-level locking
- `get_for_reconciliation(service_id)` together with its current assignment

The repository owns version allocation. Callers must not calculate versions
from a prior read.

### `ActualStateRepository`

- `get(service_id)`
- `record_observation(service_id, assignment_id, version, status,
  configuration, health, observed_at)`

`record_observation` verifies the assignment and applies the stale-version
rule atomically. It returns whether the report was accepted or ignored as
stale; an invalid assignment is a conflict, not a new assignment.

## Transaction boundaries

The Master application owns the transaction scope. The minimum atomic units
are:

1. **Placement:** lock the service's desired-state row and the selected node's
   capacity row, then create or replace the active assignment and increment the
   desired-state version before commit.
2. **Heartbeat:** update node health, usage and heartbeat timestamp in one
   transaction.
3. **Actual-state report:** validate the current assignment and upsert the
   observation only if its version is not stale, in one transaction.

Repositories participate in a caller-provided transaction but do not commit
independently. Retries of a failed transaction must be safe; agent delivery
retries reuse the same committed desired-state version.

## Explicit non-goals

- No SQLAlchemy model code, Alembic migration, or PostgreSQL deployment is
  created by this design step.
- No scheduler algorithm, failover policy, provider configuration schema, or
  REST endpoint contract is defined here.
- No direct Worker Agent database access or Agent-to-Agent communication is
  permitted.
